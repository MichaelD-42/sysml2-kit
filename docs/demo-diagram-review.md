# Demo explorer: diagram types per level

Review of the views the demo explorer (`demo/`) offers at each level of the seat-switch RFQ, against the question an engineer asks there and the SysML v2 diagram kind that answers it. Basis: the demo as built on `feat/demo-explorer` (Task 16) and the content of `examples/seat-switch-rfq` with its platform.

| Level | Question an engineer asks | SysML v2 diagram kind | Demo today | Verdict |
|---|---|---|---|---|
| Product | What is this product, who uses it, what does it consist of? | Composite overview: context, use cases, features, logical and physical breakdown (no single SysML kind; a general view) | Product overview (new, landing view): context and actors, use cases, features with function counts, logical blocks and the four positions with the variants they select, physical parts by ME/EE/SW with SW components and unit counts | Add (done in Task 16) |
| R: use cases and requirements | Who wants what from the switch, and which customer requirement says so? | Use case diagram; requirement diagram / table | Use cases (actors to use cases of the subject), Traceability (one CRS's RFLP chain), Compliance (tables), requirements tree | Keep. A requirement diagram adds nothing over the trace view and the tree for this audience |
| F: features and functions | What does a feature do, in what order, with what data? | Activity (action flow) diagram | Activity, now including the actions a feature inherits from its platform feature (FEAT-104 shows SSW-F-011..013, 022) | Keep; changed so an RFQ feature shows what it does |
| L: logical architecture | Which blocks are there and how do they connect to the vehicle? | Interconnection (internal structure) view; context view | System context, System boundary, Interfaces, Composition | Keep |
| L: behaviour over time | How does the switch go to sleep and wake on the LIN bus? | State machine (state transition view) | Nothing: the model has requirements (SSW-SR-013 busSleepAndWake) and items (GoToSleepCommand, WakeUpPulse) but no `state def` | Add later, model first: an `exhibit state` on linCommunication (awake, bus idle, sleep, wake-up) is the clearest candidate; the view is only worth building once the model holds states |
| L/P: interactions | What is the message order in a diagnostic session or a reflash? | Sequence view | Nothing: SSW-STC-020 workshopReflashTest and SSW-F-019..021 describe the flow in prose and successions only | Add later, model first: tester, seat control unit (gateway) and switch exchanging session control, security access, download and activation; a sequence of SSW-F-016 grantSecurityAccess to SSW-F-021 is the candidate |
| P: physical incl. ME/EE/SW, SW units | Which parts implement a block, which pins, which variant goes where? | Composition / tree; interconnection with ports; interface / pin table | Composition (firmware > SW components > units), Boundary (connector pins bound to ports), Interfaces, Variants (housing LH/RH, button sets, with the RFQ's selections) | Keep. A pin table would duplicate Boundary for the three pins the connector models today; revisit once the full pin-out is modelled |
| V: verification | Is each requirement tested at the right level, and did it pass? | V-model; verification case / requirement tables | V-model (levels, left and right leg, results), Compliance, Traceability, Meta-model | Keep |

Recommendations. The product level was the gap and is now the landing view. The two real gaps after it are behavioural, and both need model content before a view: a LIN sleep/wake state machine on the logical LIN block, and a diagnostic/reflash sequence. Building either view against the current model would draw an empty or invented diagram, so model them first (platform, so every RFQ inherits them) and add the view in the same step. Everything else the demo offers maps to a question at its level; no view should be dropped.
